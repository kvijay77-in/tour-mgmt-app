# Events, hotels and baggage

_Last updated: 2026-10-01_

An event definition describes activities; a dated occurrence makes them available for a tour. Authorized staff scan the appropriate rider or baggage code for activities in an active occurrence, inspect its dashboard and rider progress, and reconcile baggage at the appropriate step. Crew and hotel users see only activities allowed by their assignments. Administrators manage event definitions and occurrences; Super Users can manage occurrences but not definitions. Event scanning supports the mobile offline queue subject to local readiness and later server validation.

Definitions support ordered activities, optional variants and opt-out, prerequisite activities and allowed code types; occurrence-specific adjustments must not change the definition. Event settings control whether rider registration is required and whether riders may self-serve. Registration defaults off; when it is off, every rider on the tour is treated as registered. When enabled, registration and unregistration are available only while an occurrence is `PLANNED`.

Users with the event-registration management permission can open an occurrence's Registrations screen when registration is enabled. It lists rider ID, name, registration time and source, with search and staff register/unregister actions. Changes are online-only and available only while the occurrence is `PLANNED`; other statuses are read-only. On an unregistered-rider scan rejection, show the rider-specific message without a registration shortcut: scanning requires an `ACTIVE` occurrence while registration changes require `PLANNED` (S-6).

Self-service permission resolves from the occurrence activity override, occurrence, activity definition, event definition, then defaults to not allowed. An unset value follows the next level. Activity definitions and occurrences can explicitly allow or disallow self-service; an occurrence activity override can inherit by clearing its value. Occurrence settings may be cleared to return to inheritance. The former informational event self-service setting has been removed.

Occurrences may be started, completed or cancelled, with outstanding mandatory items counted rather than silently discarded. Scans must reject disallowed code types and duplicates. Unsent offline scans may be removed locally, while submitted scans require an authorized cancellation. Occurrence dashboards show completed, outstanding, opted-out and flagged activity counts; baggage reconciliation compares loading and unloading and identifies missing riders. Event dashboards can show the last saved snapshot offline with a stale-data indication.

When registration is enabled, event dashboards show the registered count and mark each unregistered rider. Show **Self** on cancelled records and rider progress items when their method is `SELF_SERVICE`. Event dashboard activity cells do not carry a method, so they cannot show the Self label (BC-3).

Administrators and Super Users manage hotels and room allocations online. Hotel details include an ID, name, city and address; an allocation may be adjusted for a rider and night. Bulk CSV upload either applies in full or reports all row errors without changing allocations. Room capacity and roommate compatibility are checked before accepting changes. Consult [events design](../design/events.md) and the backend [RBAC reference](https://github.com/kvijay77-in/tour-data-api/blob/main/docs/design/rbac.md).
